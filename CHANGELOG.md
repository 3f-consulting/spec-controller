# Changelog

Each line says what a change means for someone using spec-controller.

- This changelog starts: from now on, every change to spec-controller is told here in a line, except a dependency update.
- Each release's notes on GitHub are now the lines this changelog gained since the release before.
- balance posts a fitness function's CI step as passed only when the step record says it passed: a step the record does not name is posted as not recorded and credits no claim, and continue-on-error set to anything but false, an expression included, allows failure.
- balance posts a step-record entry that no workflow has with the result its record gives: a failure as failed, a skipped step as never ran, and a success as passed-on-error, since without the workflow it cannot read whether failure was allowed. A report now gives such a step its result alone, and the JSON report's Evidence Observations have no `notes` field.
- What balance does is unchanged: the specification's scenario on continue-on-error is now worded for a step in a workflow balance read, the only steps whose setting balance can read.
- Each published package names its source repository, 3f-consulting/spec-controller, on npm; the link opens once the repository is public.
- No change to the packages: the first release from spec-controller's new repository.
- spec-controller's repository is public, with every commit of its history, and from this release on each release carries its provenance on npm.
- What balance does is unchanged: two specification files read more plainly, one describing reconciliation in fewer words and one with its Rules in the order the report shows them.
- @3f-consulting/spec-controller-core exports `CreditJournal`, the Evidence Observations read from a run's reports that `claimReconciliationsOf` posts; nothing balance does changes.
- The JSON report names the version of its schema in `schemaVersion`, and the version rises whenever the report's structure changes; @3f-consulting/spec-controller-core exports the report's type, `JsonReport`, and `jsonReportFrom`, which builds it from a reconciliation.
- Every TypeScript example in the READMEs is written whole, with its imports and declarations, and CI type-checks each one against the package's own exports.
- balance refuses a Vitest, Jest, Cucumber or RSpec evidence report in which any field its reader reads is missing, null or of the wrong kind, or holds a status its runner never writes: the run stops at exit 2 and names the report and where it first breaks, where before it ended as an unexpected error or dropped the result without a word. A Cucumber step with no keyword is refused wherever it appears.
- balance lists two of a claim's Quality Check Reconciliations that tie on kind, place, cited codes and message in the order of their tests' titles, where before they kept the order their evidence came in.
- A `runners` entry can name the reports its runner writes, as `{ "runner": "playwright", "reports": ["playwright.xml"] }`, and each result in a report is evidence of the layer whose entry names that report's file name, so a Playwright or Cypress suite can answer an `@e2e` claim. A report named under several layers gives each result the layers its scenario's tags name, or all of them when it names none. A report no entry names is unit evidence, or integration evidence for a Cucumber report, whatever its scenarios' tags: name your Cucumber report under each layer it serves to keep its `@e2e` and `@performance` results at those layers. A report name that matches no report the run read is named as `runner-report-not-read`, and the JSON report's schema version rises to 2. In @3f-consulting/spec-controller-core, `targetConfigurationFrom` takes the file names of the evidence reports the run read as a third argument, each reader takes the layers its report serves, and `layersServing` gives them.
- balance reads each row of an Examples block with no clm column, in an Outline where another block has one, as an executable claim with no claim code, which reads `no-claim-code`, where before such a row raised no Evidence Obligation and the report gave no word of it.
- What balance does is unchanged: the specification's scenario on when a recorded success is passed-on-error now says balance reads continue-on-error on the step and on the step's job, the two places it reads, where before it said the workflow.
- `--vitest`, `--jest`, `--pytest`, `--junit`, `--rspec` and `--cucumber` can each be given several times, so a monorepo or a split CI run needs no step that merges its reports: balance reads every report named, posts every result in each at the layers its own file name is given in `runners`, and the provenance has a line for each.
- What balance does is unchanged: in the Markdown report, how many of a claim's tests of a kind ran, and whether a row's claim code is shared, now come from the same rules balance reconciles by, where before the report kept its own copy of each.
- What balance does is unchanged: in @3f-consulting/spec-controller-core, the executable claims a run reads are now named as the debit journal, beside the credit journal: `DebitJournal` is exported as a type, and `claimReconciliationsOf` takes the debit journal and the credit journal.
- What balance does is unchanged: two specification files say exactly how a claim's checks are ordered and where a feature file's code is declared, and the guides say a scenario Cucumber does not run states its steps in lowercase.
- What balance does is unchanged: the domain of @3f-consulting/spec-controller-core reads each input in its own words, and each reader translates its format, so a new test runner, report format or CI provider changes only its reader. Core's published types for what a reader returns are renamed for what they are, and the functions that took a format's own types take them instead. `shellAnswers` says whether a command runs the reconciler, in place of whether it runs a given program in any of its commands. `resultsByFileFrom` returns a Vitest or Jest report's `TestResult`s, and `observationsOfTestResults` posts them, in place of `observationsByFile`. `resultsBySuiteFrom` returns a JUnit or pytest report's `TestResult`s, which `observationsOfTestResults` posts, in place of `observationsBySuite`. `resultsByExampleFrom` returns an RSpec report's `TestResult`s, which `observationsOfTestResults` posts, in place of `observationsByExample`. `scenarioResultsFrom` returns a Cucumber report's `TestResult`s, which `observationsOfTestResults` posts with the feature files, in place of `observationsOfScenarios` and its `ScenarioResultAsWritten`.
- What balance does is unchanged: @3f-consulting/spec-controller-core checks whether a value read from a file is a plain object in one place, where before its workflow reader kept a copy of its own.
- What balance does is unchanged: it works out what each CI step is once, where before it did so twice. In @3f-consulting/spec-controller-core, `disposedStepsOf` gives each CI step with what it is, and `fitnessObservationsOf` takes the steps as `disposedStepsOf` gives them, with the step record, in place of the steps, the step record, the configuration, the scripts and the shell answers; `DisposedStep` is exported as a type.
- A fault in spec-controller's own code while it reads a valid input now stops the run at exit 4 as an unexpected error, naming it, where before balance or allocate refused the input as not parsing or not in its shape. A failure while the part that reports unexpected errors loads also ends at exit 4, where it ended at 1. A workflow step written as nothing is refused by name, and XML its parser refuses is refused as not parsing. @3f-consulting/spec-controller-core exports `InputDoesNotParse`, which its readers throw for an input they cannot read.
- `--ci-steps` can be given several times, once for each job's step record, so a fitness function's step in any job is read: balance posts every entry, in every record, that names a step's id, and the provenance has a line for each record. Before, a second `--ci-steps` was refused, and a step in any job but the one whose record was named read not recorded.
- allocate counts only codes written under CLM: it no longer reads the retired scenario code SCN, which no published version ever wrote. A repository still holding an SCN code with a higher number than any of its CLM codes could be given that number again.
