# Changelog

Each line says what a change means for someone using spec-controller.

- This changelog starts: from now on, every change to spec-controller is told here in a line, except a dependency update.
- Each release's notes on GitHub are now the lines this changelog gained since the release before.
- balance posts a fitness function's CI step as passed only when the step record says it passed: a step the record does not name is posted as not recorded and credits no claim, and continue-on-error set to anything but false, an expression included, allows failure.
- balance posts a step-record entry that no workflow has with the result its record gives: a failure as failed, a skipped step as never ran, and a success as passed-on-error, since without the workflow it cannot read whether failure was allowed. A report now gives such a step its result alone, and the JSON report's Evidence Observations have no `notes` field.
- What balance does is unchanged: the specification's scenario on continue-on-error is now worded for a step in a workflow balance read, the only steps whose setting balance can read.
- Each published package names its source repository, 3f-consulting/spec-controller, on npm; the link opens once the repository is public.
- No change to the packages: the first release from spec-controller's new repository.
- spec-controller's repository is public, with every commit of its history, and from this release on each release carries its provenance on npm.
- What balance does is unchanged: two specification files read more plainly, one describing reconciliation in fewer words and one with its Rules in the order the report shows them.
- @3f-consulting/spec-controller-core exports `CreditJournal`, the Evidence Observations read from a run's reports that `claimReconciliationsOf` posts; nothing balance does changes.
- The JSON report names the version of its schema in `schemaVersion`, and the version rises whenever the report's structure changes; @3f-consulting/spec-controller-core exports the report's type, `JsonReport`, and `jsonReportFrom`, which builds it from a reconciliation.
- Every TypeScript example in the READMEs is written whole, with its imports and declarations, and CI type-checks each one against the package's own exports.
- balance refuses a Vitest, Jest, Cucumber or RSpec evidence report in which any field its reader reads is missing, null or of the wrong kind, or holds a status its runner never writes: the run stops at exit 2 and names the report and where it first breaks, where before it ended as an unexpected error or dropped the result without a word. A Cucumber step with no keyword is refused wherever it appears.
- balance lists two of a claim's Quality Check Reconciliations that tie on kind, place, cited codes and message in the order of their tests' titles, where before they kept the order their evidence came in.
- A `runners` entry can name the reports its runner writes, as `{ "runner": "playwright", "reports": ["playwright.xml"] }`, and each result in a report is evidence of the layer whose entry names that report's file name, so a Playwright or Cypress suite can answer an `@e2e` claim. A report named under several layers gives each result the layers its scenario's tags name, or all of them when it names none. A report no entry names is unit evidence, or integration evidence for a Cucumber report, whatever its scenarios' tags: name your Cucumber report under each layer it serves to keep its `@e2e` and `@performance` results at those layers. A report name that matches no report the run read is named as `runner-report-not-read`, and the JSON report's schema version rises to 2. In @3f-consulting/spec-controller-core, `targetConfigurationFrom` takes the file names of the evidence reports the run read as a third argument, each reader takes the layers its report serves, and `layersServing` gives them.
- balance reads each row of an Examples block with no clm column, in an Outline where another block has one, as an executable claim with no claim code, which reads `no-claim-code`, where before such a row raised no Evidence Obligation and the report gave no word of it.
- What balance does is unchanged: the specification's scenario on when a recorded success is passed-on-error now says balance reads continue-on-error on the step and on the step's job, the two places it reads, where before it said the workflow.
- `--vitest`, `--jest`, `--pytest`, `--junit`, `--rspec` and `--cucumber` can each be given several times, so a monorepo or a split CI run needs no step that merges its reports: balance reads every report named, posts every result in each at the layers its own file name is given in `runners`, and the provenance has a line for each.
- What balance does is unchanged: in the Markdown report, how many of a claim's tests of a kind ran, and whether a row's claim code is shared, now come from the same rules balance reconciles by, where before the report kept its own copy of each.
- What balance does is unchanged: in @3f-consulting/spec-controller-core, the executable claims a run reads are now named as the debit journal, beside the credit journal: `DebitJournal` is exported as a type, and `claimReconciliationsOf` takes the debit journal and the credit journal.
- What balance does is unchanged: two specification files say exactly how a claim's checks are ordered and where a feature file's code is declared, and the guides say a scenario Cucumber does not run states its steps in lowercase.
- What balance does is unchanged: the domain of @3f-consulting/spec-controller-core reads each input in its own words, and each reader translates its format, so a new test runner, report format or CI provider changes only its reader. Core's published types for what a reader returns are renamed for what they are, and the functions that took a format's own types take them instead. `shellAnswers` says whether a command runs the reconciler, in place of whether it runs a given program in any of its commands. `resultsByFileFrom` returns a Vitest or Jest report's `TestResult`s, and `observationsOfTestResults` posts them, in place of `observationsByFile`. `resultsBySuiteFrom` returns a JUnit or pytest report's `TestResult`s, which `observationsOfTestResults` posts, in place of `observationsBySuite`. `resultsByExampleFrom` returns an RSpec report's `TestResult`s, which `observationsOfTestResults` posts, in place of `observationsByExample`. `scenarioResultsFrom` returns a Cucumber report's `TestResult`s, which `observationsOfTestResults` posts with the feature files, in place of `observationsOfScenarios` and its `ScenarioResultAsWritten`.
- What balance does is unchanged: @3f-consulting/spec-controller-core checks whether a value read from a file is a plain object in one place, where before its workflow reader kept a copy of its own.
- What balance does is unchanged: it works out what each CI step is once, where before it did so twice. In @3f-consulting/spec-controller-core, `disposedStepsOf` gives each CI step with what it is, and `fitnessObservationsOf` takes the steps as `disposedStepsOf` gives them, with the step record, in place of the steps, the step record, the configuration, the scripts and the shell answers; `DisposedStep` is exported as a type.
- A fault in spec-controller's own code while it reads a valid input now stops the run at exit 4 as an unexpected error, naming it, where before balance or allocate refused the input as not parsing or not in its shape. A failure while the part that reports unexpected errors loads also ends at exit 4, where it ended at 1. A workflow step written as nothing is refused by name, and XML its parser refuses is refused as not parsing. @3f-consulting/spec-controller-core exports `InputDoesNotParse`, which its readers throw for an input they cannot read.
- `--ci-steps` can be given several times, once for each job's step record, so a fitness function's step in any job is read: balance posts every entry, in every record, that names a step's id, and the provenance has a line for each record. Before, a second `--ci-steps` was refused, and a step in any job but the one whose record was named read not recorded.
- allocate counts only codes written under CLM, and reads none of the retired SCN codes that versions up to 0.1.246 wrote. A repository still holding an SCN code with a higher number than any of its CLM codes could be given that number again.
- What balance does is unchanged: each variants list in @3f-consulting/spec-controller-core's source is keyed by the kind of input it lists, and names the claim its tests cite, so renumbering a scenario changes no reader.
- What balance does is unchanged. In @3f-consulting/spec-controller-core, `CiStep` names its fields in the tool's own words, not GitHub Actions': `uses` is `action`, `run` is `command`, `continueOnError` and `jobContinueOnError` are `allowsFailure` and `jobAllowsFailure`. A new field every step must have, `identity`, holds the step's name, else its action, else the first line of its command that is not blank, trimmed, as the workflow reader decides it. Code that builds a `CiStep` by hand must rename those fields and set `identity`.
- What balance does is unchanged: a new evidence report format is one entry in one list, beside its reader and its lines in the message catalogue, where before it took six edits in three files. @3f-consulting/spec-controller-core exports `EVIDENCE_REPORT_FORMATS`, evidence report formats: one entry for each of the six report formats balance reads, giving its flag, its reader, whether it reads a folder, whether its results need the feature files and its default layer.
- What balance does is unchanged: a report no `runners` entry names is evidence of its format's default layer, unit for five formats and integration for Cucumber's, where before the layer was read from whether its results were scenarios. In @3f-consulting/spec-controller-core, `observationsOfTestResults` takes the report's default layer as its third argument, before the layers its report serves, and each `EVIDENCE_REPORT_FORMATS` entry gives it as `defaultLayer`.
- What balance does is unchanged: @3f-consulting/spec-controller-core exports `reconcile`, which turns what the readers gave (the feature files, the evidence reports, the CI steps and step records, the configuration settings and the rest) into the Evidence Reconciliation in one call, where before a library user made the dozen calls balance makes; balance now makes that one call.
- `allocate` takes `--features <dir>`, as `balance` does: name the folder your feature files are in, and `allocate` finds a feature code on a feature file there, inside git or outside it. Left out, it is `features/` at the top of the repository, as before.
- The report counts the scenarios a deferral tag set aside: the Summary has a line for them when there are any, and the JSON report's totals carry `deferredScenarios`, an Outline counted once and none in a strict run, so the report says how many scenarios a deferral set aside. The JSON report's schema version rises to 3. In @3f-consulting/spec-controller-core, `evidenceReconciliationOf` takes `claimReading`, the settings the claims were read with (`deferralTags` and `strict`), and counts the scenarios they set aside; `Totals` has `deferredScenarios`.
- balance posts a recorded success as passed-on-error when any workflow step carrying its id allows failure, so its claim reads cannot-fail, where before it read continue-on-error from the first step with that id only, and a success whose own job allowed failure could post as passed.
- What balance and allocate do is unchanged: three of their claims gain a test run through the command itself, so the command's own handling of a refused feature code, a Cucumber result citing its claim through an Outline row, and a target and source commit given on the command line is held by a test.
- What balance does is unchanged: @3f-consulting/spec-controller-core exports `provenanceInputsOf`, which names each input kind once for each path a run read for it, in order, and once with no path for a kind it read none of, as the provenance lists them; balance names its inputs with it.
- A merge to main publishes spec-controller under the `next` dist-tag, with no git tag and no GitHub release; a release comes once per increment, from a merge that adds a version heading, `## 0.1.<N> — <date> — <title>`, to this changelog, and publishes that version under `latest` with one tag and one GitHub release whose notes are the heading's section. `npm i spec-controller` installs the latest release, and `npm i spec-controller@next` the newest build.
- What balance and allocate do is unchanged: the repository's lint now refuses a test outside core's domain that cites a domain claim through a row of its test table, as it already refused one citing it in its title, and the specification's scenario on continue-on-error in a workflow names the step and the job it reads.
- What balance does is unchanged: the specification states once that a run with no feature files and no Evidence Observation has nothing to reconcile, where two rows said it, one for no feature corpus and one for an empty one.
- What balance does is unchanged: a release refuses a version heading that names a version other than the one it publishes, as before, and CI now checks that refusal on every change.
- What balance does is unchanged: its Vitest, Cucumber and JUnit readers are now tested against real reports copied from Vitest's, cucumber-js's, Maven Surefire's, Gradle's, gotestsum's and go-junit-report's own repositories, each with its source and licence.
- balance takes its runners, non-checks and deferral tags from its own command line, so a runner is described once, in the CI step that runs balance: `--unit`, `--integration`, `--e2e` and `--performance` each name a runner and can be given several times, the long form `<runner>:<format>:<report>` names the report it writes, `--not-check` names a step that is not a check, and `--deferral-tag` a deferral tag. balance reads `package.json` only for its scripts, never a `specController` block, and stops at `--vitest`, `--jest`, `--pytest`, `--junit`, `--rspec` and `--cucumber` as flags it does not take: move each runner to its layer's flag and each report to its runner's long form. A runner named without a report reads `runner-report-not-named` until balance can find its report itself, and a long form's report with no file at its path reads `runner-report-not-read`, naming the path. The configuration errors `configuration-unknown-key` and `runner-key-not-a-layer` are retired, and the JSON report's schema version rises. In @3f-consulting/spec-controller-core, a `Runner` is a name with an optional `ReportLocation`, each layer has a list of runners, a report is given to the domain with its runner's layers, and `RunnerEntry`, `layersServing`, `configurationSettingsFrom` and `targetConfigurationFrom` are removed.
- balance finds the evidence report of a runner named without one from the CI step that runs it: the option naming the report on the step's command, or in a `package.json` script the step runs, read from the step's working directory, for Vitest, Jest, pytest, cucumber-js, RSpec, Playwright and gotestsum, so `--unit vitest` is the whole setting of a Vitest suite whose CI step writes a report. A runner whose report balance cannot find this way reads `runner-report-not-named`, which a long form answers. In @3f-consulting/spec-controller-core, a `CiStep` holds its working directory and its environment, and `ShellAnswers` names the reports a step's command writes for a runner.
- balance reads a Maven or Gradle runner's evidence reports from where the runner writes them by default, when no CI step that runs it names a report: `target/surefire-reports` for `mvn test` and `./mvnw test`, and `build/test-results/test` for `gradle test` and `./gradlew test`, each joined with the step's working directory. So `--unit "mvn test"` is the whole setting of a Maven suite. In @3f-consulting/spec-controller-core, `ShellAnswers` gives a runner's default locations, and `reportsLocatedOf` takes them as the last resort.
- `balance --written-claims-only` counts only the executable claims in the run verdict: tests that cite no scenario, or one nobody wrote, are still listed and do not turn the run red, so a team can gate on the scenarios it has named. The report's provenance says when the verdict counted only those claims. In @3f-consulting/spec-controller-core, `reconcile` and `evidenceReconciliationOf` each take `countOnlyExecutableClaims`, `Provenance` gains `countedOnlyExecutableClaims`, and `provenanceOf` gives a `ProvenanceOfInputs`, the provenance without that field; both types are exported. The JSON report's schema version rises to 5.
