# spec-controller

**Reassurance that your software keeps doing what you said it does.**

Software built from a written specification has three artefacts, and each link between them needs holding:

| Link | What holds it today |
|---|---|
| tests ↔ code | **Mechanism**: the tests themselves, coverage, mutation testing |
| spec ↔ tests | **Nothing but care.** The spec says one thing, the tests prove another, and nothing notices when they drift |
| spec ↔ code | only through the other two |

`spec-controller` holds the middle link. Each behaviour your spec names is a scenario in a `.feature` file, tagged with the evidence it needs, such as `@unit` or `@e2e`. On every CI run, `balance` reconciles those scenarios against the test reports and CI steps that actually ran, and turns the build red when the two disagree.

This is what it prints. The sample is generated by the CLI from a committed example, and CI checks it, so it cannot drift:

Read it as a ledger. Each scenario is an account. Its tags are what it is owed, and the evidence that ran is what it was paid. One account balances, one test is failing, one scenario has no test at all, a test cites a scenario that doesn't exist, and a test cites nothing.

## What double entry buys: a change becomes deliberate

Every behaviour is recorded twice, once as a scenario and once as the test that proves it, and the two must agree. So **changes to your quality checks become deliberate, not accidental.**

- **Delete a test** and its scenario reads `missing`. The build goes red.
- **Re-point a test** at another scenario and the original reads `missing`.
- **Delete a scenario** and its test reads as citing a scenario that doesn't exist.

To remove a behaviour cleanly, you change both places, the scenario and its evidence. That change shows in the diff, and review judges it.

This matters most where code is written by an agent. Asked to make failing tests pass, an agent can delete them. Here that is a red build, not a quiet green.

**The limits, said plainly:**

- **Deliberate is not right.** A two-place change balances; whether it should have been made is for review.
- **A change inside one check is one entry, and is not seen.** A lint step narrowed to match no files still exits 0, and its row reads satisfied. A row checks that the step ran and what it reported, read from your CI run's own record, so a red that `continue-on-error` swallowed still reds its row. It does not read what the tool examined.
- **No named behaviours, no second entry, no protection.** Code that arrives with no scenario raises nothing to reconcile.
- **Whether a test is a good test is assumed.** A balanced row means the evidence exists and holds, not that it tests what the title says.

## Why not coverage or mutation testing?

They are good at their own questions, and both live at the unit tier:

| Tier | Coverage | Mutation testing | `spec-controller` |
|---|---|---|---|
| `@unit` | yes | yes | yes |
| `@integration`, `@e2e` | rarely collected, and counts lines | possible, slow, rare | yes |
| `@performance` | no such idea | no such idea | yes |
| `@fitness` (lint, complexity, type checks, any CI check) | no such idea | no such idea | yes |

Coverage and mutation testing guard tests ↔ code. Neither can see the spec, so neither notices a named behaviour with no proof, or a passing test that proves a different behaviour from the one it cites. `spec-controller` is one ledger across all five tiers.

**For a well-tested team at the unit tier, it adds hygiene, not discovery.** Above the unit tier, once behaviours are named, nothing else holds the link. Keep your coverage gate and your mutation threshold; they are inputs here, not rivals.

## What it found on a real codebase

On its first run over another product of ours, `balance` balanced 228 of 229 scenarios. The one exception was real: two passing unit tests cited a scenario that asked only for end-to-end evidence. That product's CI was green, and it had no way to notice. The fix was to move each test's citation to the scenario it really proved.

## Who it fits

- **CI:** GitHub Actions. The run's own step record is how a CI check becomes evidence, so this is the real requirement.
- **Unit evidence:** Vitest's JSON report, or pytest's JUnit XML (`--pytest`).
- **Integration and end-to-end evidence:** any Cucumber implementation's JSON report, in any language.
- **Fitness evidence:** any check your pipeline runs, in any language.
- **The spec:** a list of named behaviours in `.feature` files. Unit-level scenarios need no step definitions: a title and its tags are the whole scenario. A Vitest test cites it in brackets in its title, `[SCN-<FFF>-<NNN>]`, and a pytest test with `@pytest.mark.scn`.

## Try it

```
npm install -g spec-controller
```

Requires Node ≥ 22. Then, from your repository:

```
spec-controller balance \
  --features ./features \
  --vitest ./vitest-report.json \
  --cucumber ./cucumber-report.json
```

Give it whichever reports you have. [`doc/how_to_use.md`](./doc/how_to_use.md) → *What you need* says how to produce each one.

`balance` is a gate: an out-of-balance run exits `1`. To watch before you gate, add `--exit-zero`: the same report, exiting `0` on an out-of-balance verdict. Remove the flag when you're ready to gate. On GitHub Actions, `--format md:$GITHUB_STEP_SUMMARY` puts the report on the run's summary page.

**Before you name anything, it lists what ran.** With no scenarios, every test and CI step is reported, grouped by file, with what passed and what failed. That tells you nothing your CI doesn't already show. It is a starting inventory, and the value begins when you name the behaviours. Setup steps your pipeline runs (publishing, version bumps) are listed as checks until you name them in `specController.notChecks`. GitHub's own checkout, setup, cache and artifact actions are left out for you.

The full flags, CI wiring and a worked example are in [`doc/how_to_use.md`](./doc/how_to_use.md).

At `0.x` nothing is promised between versions ([`doc/compatibility.md`](./doc/compatibility.md)). Pin an exact version.

## Built with Claude Code, and how it's kept honest

This repository was built with Claude Code, by an author who doesn't write TypeScript. The commit history is the agent's working log: each title follows the issue-key convention, `[KEY-123] summary`, and the ID refers to a private tracker. It is held by the same discipline it sells. Its own CI reconciles its own scenarios with `balance` on every run, and gates on:
- mutation testing at 95% per scope;
- cognitive complexity, function length and CRAP;
- duplication and unused code;
- dependency boundaries;
- published-package checks (publint, attw);
- workflow linting and security (actionlint, zizmor);
- a ceiling on test code against production code.

**Why these gates:** each fitness function this repository runs in CI is a scenario in [`features/fitness-functions.feature`](./features/fitness-functions.feature), and its Rule says what it holds and why. Each gate automates a kind of feedback a technical lead gives in code review, so a reviewer's attention goes to design and intent.

It has been caught. Claude Code once re-pointed two live tests at scenarios they did not prove, to clear this tool's own red. Review caught it, and the change was reverted. That is the limit above in practice: a two-place change balances, and review is what judges it.
