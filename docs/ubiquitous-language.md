# spec-controller's ubiquitous language

This glossary lists the words spec-controller's code, scenarios, report and help use, and what each means. It has two parts. The **domain terms** are spec-controller's own, and this file defines them. The terms **borrowed from 3F Consulting's delivery methodology** are only named here. That methodology is not published, so [`user-guide.md`](./user-guide.md) describes them where it uses them.

Each definition comes from the maintainers' domain model and the scenarios they endorsed, never from the code. Where this file and the code disagree, the domain model decides, and whichever is wrong is corrected.

**One vocabulary across every surface**: code identifiers, JSON keys, Markdown headings, and a database schema if there ever is one. You read a machine key as much as you read prose, so machine keys get no private dialect.

**One term, three forms — the form follows the surface, the word never changes, and a term from this file is `backticked` wherever it appears.**

- Prose spells it out: `phantom claim`, `kind of quality check`.
- A handle hyphenates it: `static-check`, `phantom-claim`, `quality-check-kind`, `no-quality-check`.
- A code identifier camel-cases it: `phantomClaim`.

A handle is not a licence to abbreviate. `claim` is not a short form of `phantom-claim`; it is a different word.

The **Double-check** entry of an evidence-model term lists words that have been seen standing in for it. Such a word means the term only where it is used in the term's sense.

## Domain terms

### The evidence model

Correctness is the agreement of two independent records. The debit side is the `Evidence Obligations` written in the test specifications. The credit side is the `Evidence Observations` seen when those tests run against the real code. Each term names the bookkeeping term it borrows, which explains the analogy.

#### The subject

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Behaviour` | One thing the **`Application code`** should do, stated so it can be proved. A behavioural scenario's claim is an example of one `behaviour`. A fitness function's claim is not a behaviour: it is a whole-system property against a threshold. A `behaviour`'s `Evidence Obligations` are the ones its scenario raises, one for each `kind of quality check` the scenario names. Its `Evidence Observations` exercise it against the real code. The **`Test Specification`** exists to describe `Behaviour`. A behaviour is the reason a scenario is written at all, and it is what `never-ran` says was never exercised. | Transaction — the real-world event an entry records | feature; functionality |
| `Application code` | The system under test: the reality that `evidence observations` are evidence of. It is on the credit side, but it is *not an entry itself*. | *(the subject the books describe)* — the real-world thing the accounts account for | |
| `Document specification` | Written intent: a document saying what the **`Application code`** should do, covering its behaviour and its fitness. A manifesto, a proposal and a technical design are examples. A document is needed to make intent clear enough to build from. It is never sufficient, because a document is not evidence. It is meant to live briefly: once **`executable specifications`** express it, they are the current truth. `balance` never reads one, so whether the checks say what the document says is judgement, not reconciliation. | Source documents — the contracts and invoices the entries are vouched against | spec, the spec (unqualified, where it could mean either kind) |
| `Executable specification` | A specification that states what the application must do and that a `quality check` runs against it: a scenario, a unit test or a fitness function. It is the preferred kind of specification, because running it is the evidence. The **`Test Specification`** is the collection of them. | *(the entries themselves)* — what the books record | living documentation (the field's other name, kept as a synonym); the Gherkin spec |

#### The `claims` — an executable claim, a phantom claim or an unnamed claim

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Claim` | What one `Claim Reconciliation` is about: a statement the evidence is weighed against. A claim is one input and one outcome. There are three kinds. An **`executable claim`** is a scenario, or a row of an Outline with a `clm` column. A **`phantom claim`** is named by evidence and written nowhere. The **`unnamed claim`** is for evidence that names no claim. Every `evidence observation` lands on exactly one claim, and each claim has one **`Claim Reconciliation`**. In the JSON report, each Claim Reconciliation's `claim` key describes its claim. For an executable claim, it gives the `file`, `title`, `obligations` and, when there is one, `claimCode`. For a phantom claim, it gives the `claimCode` alone. For the unnamed claim, it gives nothing. | *(the thing an account is opened for)* — the subject an account is kept about | real or invented scenario; invented scenario |
| `Executable claim` | A claim written to be executed, on the surface of the `quality checks`: a scenario, or a row of a Scenario Outline with a `clm` column. Its tags raise its `evidence obligations`. Its implementations (unit tests, step definitions, performance tests, CI steps) cite its claim code. `balance` shows whether both layers are there: the surface and its implementations. A balanced executable claim is one whose implementations answer every check it asks for. A *missing* one is one whose implementation layer has given no evidence. An `executable claim` is an entry in the debit journal. An **`evidence observation`** cites its claim code to post against it. A claim in a `document specification` is not an executable claim until it is written on the surface. | *(the thing an account is opened for)*: an account opened for a real subject | feature-file claim; written claim; specified claim; scenario (for the kind, since a row of an Outline with a `clm` column is one too) |
| `Phantom claim` | A claim the evidence names and nobody wrote: a cited claim code that no `executable claim` has. It gets a `Claim Reconciliation` (`outcome` *cites-unknown-claim*). There is one per fabricated code, and it is always out-of-balance. Evidence citing the code of a deferred scenario also lands on one, because a deferred scenario is not an `executable claim`. | Posting to a non-existent account — a posting naming an account that does not exist | ghost (as a top-level kind); undeclared (for a fabricated scenario); phantom scenario |
| `Unnamed claim` | The placeholder claim that gets a `Claim Reconciliation` when no single `executable claim` can take its `evidence observations`. It takes the observations that ran citing no claim code, several codes, or a code several `executable claims` share, and those posted as not recorded (`outcome` *cites-no-claim*). It also takes those that never ran and name no claim, or a code several `executable claims` share (`outcome` *never-ran*). It is one bucket, always out-of-balance. An `evidence observation` that never ran and names a claim posts to that claim's `Claim Reconciliation`. | Suspense account — an account holding postings that match no real account | unattributed (as a top-level kind); suspense scenario; observed claim |

#### The debit side

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Test Specification` | The **`executable specifications`** taken together: feature files (`@`-tags), step definitions and test code. It records the **behaviours** to be proved and the `Evidence Obligations` for each. | Source documents for debits — what the debit journal is read from | |
| `Debit journal` | The `executable claims` read from the `Test Specification` for one run, each with its `Evidence Obligations`. Posting moves each one to its `Claim Reconciliation`. The journal is then discarded. | Journal — the book of original entry, posted from | ledger (for the journal) |
| `Evidence Obligation` | An `executable claim` raises one for each `kind-of-quality-check tag` that applies to it. `Evidence Observations` must meet it. The scenario's `@`-tags name those kinds: the `layers` `@unit`, `@integration`, `@e2e` and `@performance`, and `@fitness`. A row of an Outline takes its Outline's tags. A deferred scenario raises none. | Debit — the entry for what an account requires | demand, declare, require, insist, expect — every inflection (demanded, demander, declared, undeclared, required, requirement, …); obligation (bare); the `Declared` prefix |

#### The credit side

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| Test run reports | The reports that the runners of the behavioural quality checks write, such as Vitest's and Cucumber's: reality's record. A fitness function's record is the CI run's `step record`. | Source documents for credits — what the credit journal is read from | |
| `Credit journal` | The `Evidence Observations` read from the test run reports and the step records for one run. Posting moves each one to the claim its code names. The journal is then discarded. | Journal — the book of original entry, posted from | ledger (for the journal) |
| `Evidence Observation` | One reported result of a test or a fitness function. It has one shape whatever its source: the codes it cites, its result (passed, failed, passed-on-error, never-ran or not recorded), its `kind of quality check`, where to look, and what it said. It posts by the code it cites. It goes to the one `executable claim` that has the code, to a `phantom claim` when no `executable claim` has it, and otherwise to the `unnamed claim`. An `evidence observation` that never reached its assertions is `never-ran`: it was reported, but did not run to a result. An `evidence observation` whose CI step no step record names is not recorded. `balance` cannot say how it went, so it is never passed and never credits a claim. | Credit — the entry for what an account is provided | observation (bare); credit, credit side (in a sentence that names no debit); supply; execution; declared (for evidence) |

#### Posting

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Quality Check` | One check, either a behavioural check or a fitness function, that assesses the product against a quality characteristic. Each `evidence observation` a quality check produces has one **`kind of quality check`**, and is matched on that kind. One run can produce evidence of more than one kind, as one `cucumber-js` run serving two `layers` does. A **`Quality Check Reconciliation`** matches an `evidence obligation` with an `evidence observation` of the same `kind of quality check`, within one `claim`. | *(the instrument a credit is booked from)* — one source of entries | check (bare) |
| `Kind of quality check` | A **`kind of quality check`** (`kind` in the JSON report) is the key an evidence obligation is raised by and its evidence is matched on. There are five, all flat peers: the four **`layers`** `unit`, `integration`, `e2e` and `performance`, and `fitness`. A scenario names its kinds of quality check by its tags, and raises one `Evidence Obligation` per tag. A check of a **`layer`** is an example of a `behaviour` on a stepped scenario. A **fitness** check is a whole-system property against a `threshold`. **One `@fitness` scenario is one check**: its claim code identifies it and its title describes it. Several fitness functions are several scenarios, as the CI pipeline's two timed suites are two. Nothing classifies a fitness function further: no characteristic word, no roster, no roll-up. The behavioural/fitness grouping exists in the model and the docs, **never in the tag**: no `@behavioural=unit`, no `@fitness=complexity`. However a fitness function gets its evidence, it posts the same way: its evidence observation cites its claim code (see `citation`). The prototype of the fitness shape is the CI pipeline timing its own suites: an `@fitness` scenario, with the measured time citing its claim code. It is never carved out as harness, and never named so as to dodge reconciliation. | *(the sub-account coordinate)* — the key an entry is classified and matched by | quality check (for one of the five); tier (for a layer); runtime (for the layers `@unit`, `@integration`, `@e2e`, `@performance`); level, (kind, level) — the two-axis grid; `lint` (as a catch-all for fitness functions); characteristic (a word classifying a fitness function); `@fitness=<check>` or any group-prefixed check tag |
| `Layer` | One of the four behavioural kinds of quality check: `unit`, `integration`, `e2e` and `performance` (`Layer` in the code). When the run names a runner for a layer, that runner runs the layer's tests or scenarios. `fitness` is the one kind of quality check that is not a layer. | | tier; behavioural check (for a layer) |
| `Claim Reconciliations` | The `evidence obligations` (debits) and `evidence observations` (credits), organised by **`claim`** with one `Claim Reconciliation` for each, and keyed by `kind of quality check`. Reconciliation happens here. The **`Evidence Reconciliation`** is the whole: the `Claim Reconciliations` and the `Summary` over them. **Every `evidence observation` posts to exactly one `Claim Reconciliation`, never to none.** An `evidence observation` that posted nowhere would vanish from the books. The `Claim Reconciliations` exist to make that fault impossible. An `evidence observation` that cites the claim code of one `executable claim` posts there, whatever its `kind of quality check`. An `evidence observation` that cites no real `executable claim` still posts, to a **`phantom claim`** or the **`unnamed claim`**. Posting is not classifying: an entry posts here whatever it later reconciles to, including nothing. | Ledger — the accounts with their posted debit and credit entries, by account | ledger (for the collection) |

#### Reconciling

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Balancing off` | Reconciling one `claim` into its `Claim Reconciliation`: its `evidence obligations` against its `evidence observations`, matched on their `kind of quality check`. | Balancing off — computing one account's balance | |
| `Quality Check Reconciliation` | One entry of a `Claim Reconciliation`, with its own **`outcome`**. An entry is one of four things. It is an `evidence obligation` with the `evidence observation` of its `kind of quality check` that answers it. Or it is an `evidence observation` with no `evidence obligation` to answer. Or it is an `evidence obligation` that no `evidence observation` that ran answers. Or it is neither, for a claim with a claim code that asks for nothing and has no evidence. A claim with no claim code that asks for nothing has one entry, `no-claim-code`, with neither side. No entry stands in for another `evidence observation`: two passing tests are two *satisfied* entries, and a passing and a failing test are one *satisfied* and one *failing* entry. Entries are sorted by `kind of quality check` (unit, integration, e2e, performance, fitness), then by where their tests are, then by the codes they cite and the rest of what each records. So two runs over the same evidence list them in the same order. The Markdown lists the entries that are not *satisfied* as the claim's `reconciling items`. | Line item — one entry in an account | sub-account; reconciled evidence obligation; line; item; picked outcome |
| `Outcome` | The eleven-valued result of a `Quality Check Reconciliation`: `satisfied`, `failing`, `cannot-fail`, `missing`, `no-claim-code`, `duplicate-claim-code`, `not-asked-for`, `cites-unknown-claim`, `cites-no-claim`, `never-ran` and `no-quality-check`. It is one thing in two representations. The **`outcome` handle** is the short machine name that the code and both reports use (`missing`, `not-asked-for`). The `outcome` itself is the sentence the reconciliation asserts. The sentence is the valuable half, because it is checkably true or false of a case; the handle is only a label. Settle a dispute by asking whether the sentence is true of the case, never by arguing about what the handle connotes. | *(whether a sub-account balances, and how)* — the balance-status of one sub-account | state; outcome tag (a `tag` is authored in a feature file; a handle is computed); the flat triad attributed / ghost / unattributed; `undemanded` (for `not-asked-for`); uncoded (for `no-claim-code`) |
| `Claim Reconciliation` | The evidence reconciled for one **`claim`**: its `Quality Check Reconciliations`. It has a **`verdict`** and its **`reconciling items`**. Its claim is one of three kinds: an **`executable claim`** (written in a feature file), a **`phantom claim`** (cited, but defined by no feature), or the **`unnamed claim`** (evidence citing no code, several codes, or a code two scenarios share). The collection is the **`Claim Reconciliations`**, *never* scenarios or `claims`, because each one is the reconciliation of a claim, not the claim. | Account — the record for one thing that carries a balance | account; scenario balance; scenarios (for the collection); Scenario Reconciliation |
| `Verdict` | The **two-valued** roll-up of a `Claim Reconciliation`. There is never a third value. It is *balanced* when every `Quality Check Reconciliation` on it is *satisfied*, and *out-of-balance* when there is any `reconciling item`. A `phantom claim`'s or the `unnamed claim`'s reconciliation is always out-of-balance. An `executable claim` with no `evidence obligation` and no `evidence observation` is out-of-balance via `no-quality-check`, or via `no-claim-code` when it has no claim code. It never gets a separate "empty" `verdict`. An `executable claim` whose tests run untagged is out-of-balance via `not-asked-for`. One that asks for a quality check under a claim code another claim shares is out-of-balance via `duplicate-claim-code`. | Balanced / out of balance — an account whose two sides agree / don't | |
| `Reconciling item` | A `Quality Check Reconciliation` whose `outcome` is not *satisfied*. An out-of-balance `Claim Reconciliation` lists every one, each typed and none ranked. There are three shapes. A debit-side exception is missing / failing / `cannot-fail` / no-claim-code / duplicate-claim-code. A credit-side exception is cites-unknown-claim / cites-no-claim / not-asked-for / never-ran. **Neither** is a real `executable claim` with a claim code, no `evidence obligation` and no `evidence observation` (no-quality-check). no-claim-code is always debit-side, because the claim code is missing from the scenario, whether or not the claim asks for a quality check. | Reconciling item — a line explaining a difference between two records | |
| `Cannot-fail` | The *`cannot-fail`* `outcome`: a passing `evidence observation` whose check's CI step or job sets `continue-on-error` to anything but `false` (`true`, or an expression such as `${{ matrix.experimental }}`). Its red might not fail the CI run. It is green on the outside, and nothing behind it need hold the build. It is read from the step records: such a step's recorded success is *cannot-fail*. A swallowed red is answered by the step's own `outcome`, so it reads *failing*. A step no step record names is not recorded, never *cannot-fail*. A recorded success whose step is in no workflow `balance` read is *cannot-fail*, because `balance` cannot read whether it allows failure. A step record does not say what the check examined, so a check over zero files that exits 0 is *satisfied*, not a pass that cannot fail. | | fabricated; green-but-fake |

#### The whole run

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Evidence Reconciliation` | The whole reconciliation. It has the `Claim Reconciliations`; the `Summary` over them, with the `run verdict`; the step account; the provenance; and the errors in the inputs and the run integrity, each empty when the run had none. It is the key concept the domain models, and the report renders it. | Trial balance — the statement of all account balances | trial balance (kept as the bookkeeping root of the metaphor); self-reconciliation, `self-balance` (names for the reconciliation check) |
| `Summary` | The report's `## Summary` section: the *Run verdict*, then the totals. The totals count the `Claim Reconciliations` (total, balanced and out of balance), the claim codes written where no claim reads them, and the scenarios a `deferral tag` set aside. They count the `Quality Check Reconciliations` by `kind of quality check`: each kind with its `Evidence Obligations`, its `Evidence Observations` and a count for each `outcome`, a row for what names no kind, and an *All* row over them. They count the `Evidence Observations` by the kind of claim they were filed on. They add *Out of balance by feature* when any claim is out of balance. The section's JSON key is `totals`. | *(the totals — no distinct classic term)* — the aggregate of the trial balance | headline tallies |
| `Claim code errors` | A whole-run section of the report that lists faults in the claim **codes** themselves. It is inside `## Errors in the inputs` (`errorsInTheInputs` in the JSON), and its JSON key is `errorsInTheInputs.claimCodeErrors`. **`foreign-claim-code`**: a scenario's code names a feature other than the one it is in. **`no-feature-code`**: a feature file declares no feature code, but its scenarios have ids. **`duplicate-feature-code`**: two feature files claim one feature code. **`several-claim-codes`**: one scenario has more than one claim code. As for an evidence observation citing several codes, no reader picks one, so the scenario raises its evidence obligations under none of them. **`claim-code-beside-clm-column`**: an Outline has a claim code, of its own or on an Examples block, and also a `clm` column. It raises its evidence obligations under neither its code nor any row's. The section is **neither a `reconciling item` nor a roll-up of `verdicts`, and on its own it leaves the run not reconciled** (`claim-code-errors`). So a run can fail for a reason that is not any `executable claim`'s `verdict`. The first three leave every posting unambiguous: what is wrong is the codes, not a `Claim Reconciliation`'s balance. A duplicated claim code is deliberately **not** in this section. Each `executable claim` with that code is its own `Claim Reconciliation`, which cannot reconcile, so it appears in the rows as `duplicate-claim-code`. Evidence citing the code credits none of them and posts to the unnamed claim. | *(a fault in the chart of accounts, not in any account)* — the books cannot be read until the coding is fixed | chart of accounts; coding errors; uncoded (for `foreign-claim-code` or `no-feature-code`) |
| `Unsound` | A run with any `never-ran` `Quality Check Reconciliation` is **`unsound`**. This is a derived whole-run reason, not an `outcome`. The run is `not reconciled`, exit 3, because its evidence could not be trusted to reconcile. It comes before every other reason. | | |
| `--strict` | The run mode that reads every claim as if nothing were deferred. A `deferral tag` is ignored, so its scenario is an `executable claim`. `@<quality-check-kind>pending` is read as `@<quality-check-kind>`, and raises that `evidence obligation`. An unmet one then puts the run out of balance, like any other. | | |

### The commands and the run

| Term | Meaning |
|---|---|
| `balance` | spec-controller's command that reconciles a target. It reads the target's `executable claims` from its feature files, and its evidence from the `test run reports` and the CI `step records`. It reconciles them into an `Evidence Reconciliation` and writes the report from it. It ends with its `run verdict`'s exit code: `0` balanced, `1` out of balance, `3` not reconciled; or `2` for a usage error and `4` for an unexpected error. |
| `allocate` | The command that prints the next claim code for a feature code: one past the highest number a claim code under that feature code has ever had in the repository. |
| evidence report | A report a test runner writes, which `balance` reads as runtime test evidence: the Vitest, Cucumber, pytest, Jest, JUnit or RSpec report. Each is named by its own flag. |
| report of test results | An evidence report of tests that are not scenarios run step by step: the Vitest, Jest, pytest, JUnit or RSpec report. Its fallback is `unit`. |
| report of scenario runs | An evidence report of Gherkin scenarios run step by step: the Cucumber report. Its fallback is `integration`. |
| fallback | The `kind of quality check` at which an evidence report posts an evidence observation. A report of test results posts every observation there. A report of scenario runs posts an observation at each `layer` its scenario is tagged with (`@integration`, `@e2e` or `@performance`), and at its fallback only when the scenario has none of those tags. |
| `--exit-zero` | Writes the same report as without the flag, but exits `0` when the run verdict is out of balance. It never changes the exit code of a run that is not reconciled (`3`), a usage error (`2`) or an unexpected error (`4`). It is the on-ramp before gating. |
| run verdict | What the whole run comes to, and its exit code: `balanced` (`0`), `out-of-balance` (`1`), or `not-reconciled` (`3`) with the reason. When several reasons apply, `unsound` comes first, then `claim-code-errors`, then `nothing-to-reconcile`. All of them come before out of balance. A run that cannot reach a verdict gives none. A run that reaches its verdict keeps that verdict's exit code. |
| not reconciled | The run verdict of a run `balance` cannot rely on. It names the reason: `unsound`, when some evidence never ran; `claim-code-errors`, when a claim code is misfiled; or `nothing-to-reconcile`, when there are no Claim Reconciliations. It exits `3`, even under `--exit-zero`. In the JSON it is `runVerdict.verdict` `not-reconciled`, with `runVerdict.why`. |
| nothing to reconcile | There is no Claim Reconciliation at all, so the run has no basis for a verdict. It is `not reconciled` (exit `3`). |
| unexpected error | An error nothing else handles. Before the run verdict, it stops the run with no verdict, at exit `4`. After the run verdict, the run keeps its verdict's exit code. |
| usage error | A malformed invocation, refused before anything runs (exit `2`). |
| error code | The stable code every refusal shows its reader in square brackets, such as `[unknown-flag]`. With it, the refusal can be quoted and looked up in the user guide, whatever its wording. An error in the inputs gives its code in the report. An unexpected error's line shows `unexpected-error`. Nothing that is not an error has an error code. |
| target | The repository being reconciled. `--target` names it in the report's provenance. Without the flag, the provenance names the git checkout's `origin`, or `unknown-target`. |
| provenance | The report's record of what was reconciled: the target, its source SHA, the tool SHA when there is one, the tool version, the time the run started, and the inputs the run read, with their paths. It makes a reconciliation reproducible and attributable. Its JSON key is `provenance`. |
| Evidence Observations (the total) | The `Summary`'s count of evidence observations over every `kind of quality check`, fitness included, and its balancing identity. Every evidence observation lands on an `executable claim`, a phantom claim or the unnamed claim, and the three counts sum to the total. |
| errors in the inputs | The report section `## Errors in the inputs` (`errorsInTheInputs` in the JSON). The Markdown prints it only when the run found errors. The JSON always includes it, with empty lists when there are none. It lists the `Claim code errors` and the `configuration errors`, each as a line giving its code, then what it is about. |

### Fitness functions in CI

| Term | Meaning |
|---|---|
| pipeline step | A step of a CI job, as the pipeline declares it: it runs a command or uses an action. |
| action | The action a `pipeline step` uses, as the workflow names it. It is a published action, named by its repository and version, such as `actions/checkout@v4`; one kept in the repository, such as `./.github/actions/setup`; or a Docker image, such as `docker://alpine:3`. |
| command | The shell lines a `pipeline step` runs. |
| non-check | A step the run names with `--not-check`, unless it is a reconciler step. The `step account` counts it under *Non-checks* (`nonChecks` in the JSON). Double-check: *Excluded* has been seen standing in for it, and means a non-check only where it is used in this sense. |
| plumbing step | A step that only sets up the job: it checks out the source, caches, sets up a toolchain, or moves artefacts between jobs. It is neither a check nor a runner. The CI workflow's reader says which steps are plumbing. The `step account` counts them under *Plumbing* (`plumbing` in the JSON). A plumbing step that the run also names as a non-check is a non-check, and is counted with the non-checks. |
| variant | One of the ways of writing an input that `balance` treats as the same, such as a launcher (`npx`, `uv run`) before a runner, or a package manager's way of running a script. One claim stands for each kind of input. Its variants are listed in a `*.variants.json` data file beside the code that reads them. The file is keyed by the kind of input, and names the claim its tests cite. There is one such file for each of these: the shell reader, the workflow reader, the reader of the settings a run names, the Vitest and Jest reader, the Cucumber reader, the RSpec reader, the Markdown report's quoting of names, the reading of a claim code in a scenario's title, and the posting of a step's continue-on-error and of a report's results by its kind. [`shell.variants.json`](../packages/core/src/inputs/shell.variants.json) lists the ways a step's command reaches a runner: the launchers, the wrappers and `xvfb-run`'s options, the package managers' ways of running a script, the runners named in several words, the command lists a runner may stand in, and the pipes onward that leave it a check. [`workflows.variants.json`](../packages/core/src/inputs/workflows.variants.json) lists the places a step can write the step record from (`run:` and `env:`) and the plumbing actions. A way of writing an input that is not listed is not read as that kind. Double-check: *form*, *spelling*. |
| fitness function | A quality check that asserts something true of the codebase or the pipeline as a whole, against a threshold. It is its `@fitness` scenario: one tool's run over one configuration, in one CI step whose `id:` is that scenario's claim code. Its evidence observation cites that code only when the `step record` names its step. A step no step record names is posted as not recorded, citing no code. |
| uncited fitness function | A fitness function whose step cites no claim. Its `evidence observation` lands on the unnamed claim. |
| step account | The report's account of the CI steps the run read: `## Step account` (`stepAccount` in the JSON). The Markdown prints it when the run read a CI workflow step, so that every step read is accounted for. The JSON always includes it, with no rows when no step was read. It has one row per workflow and job. Each row counts the steps read, then the steps by disposition (runners, reconciler steps, non-checks, plumbing, fitness functions). A total over the rows follows, which the Markdown prints when there is more than one job. A step the run read counts as a fitness function when it is not a runner the run names, the reconciler, a non-check or a plumbing step. It also counts as one when it is a runner step whose `id:` is a claim code a step record has. |
| check step | The CI step that already runs a check, with the check's claim code as its `id:`. |
| citation | An `evidence observation`'s naming of its claim's code, in the form its runner writes. One citation names one claim. The user guide gives each runner's form, and what is not read → [*How your evidence finds its scenario*](./user-guide.md#how-your-evidence-finds-its-scenario). |
| step record | One job's record of how each of its steps ended. `toJSON(steps)` writes it, and `--ci-steps` names it. `balance` reads every one the run names. |

### Configuration

| Term | Meaning |
|---|---|
| configuration setting | A setting a run names on `balance`'s command line: a runner of a `layer` (`--unit`, `--integration`, `--e2e` or `--performance`), a non-check (`--not-check`) or a deferral tag (`--deferral-tag`). Each flag may repeat. `package.json` is read only for its `scripts`. |
| runner | A program that runs a `layer`'s tests or scenarios, named by that layer's flag. A layer may have several runners, and has none when the run names none. A runner is named alone, as `<runner>`, or in its `long form`. |
| long form | A runner written `<runner>:<format>:<report>`, split at its first two colons: the runner, the format of the evidence report it writes (`vitest`, `jest`, `pytest`, `junit`, `rspec` or `cucumber`), and that report's path. `balance` reads the report, and posts its results at the runner's layer. A runner named alone names no report. |
| `--not-check` | Names a step that is neither a runner nor a check. It is written `<workflow file>:<job id>:<step name>` and matched exactly. A matching step is reported as a non-check, unless it is a reconciler step. A `--not-check` that matches no step of a workflow the run read, or does not name a step in that form, makes no step a non-check. It is named among the configuration errors. A `--not-check` naming a workflow the run did not read is not judged. |
| configuration errors | The configuration settings the run could not use, listed in `## Errors in the inputs` (`errorsInTheInputs.configurationErrors` in the JSON). They are: a setting in a form its flag does not take, left out (`configuration-wrong-kind`); a runner named alone, which names no report (`runner-report-not-named`); a `long form` whose report has no file at its path (`runner-report-not-read`); or a `--not-check` that matches no step (`not-checks-entry-matches-no-step`) or names none (`not-checks-entry-not-a-step-name`). A runner with either report error is kept, and no result of it is read. The report names each one, and none refuses the run. |
| deferral tag | A tag that defers a scenario. The scenario is not an `executable claim`, raises no evidence obligation, and posts nothing. Evidence that still cites its code lands on a `phantom claim`. The built-in set is `@wip`, `@ignore`, `@skip`, `@todo` and `@pending`, and `--deferral-tag` extends it. Under `--strict` deferral tags are ignored. The `Summary` counts the scenarios a deferral tag set aside, counting an Outline once (`totals.deferredScenarios` in the JSON). |
| `@<quality-check-kind>pending` | A tag that raises nothing: the scenario asks for no evidence of that one `kind of quality check`. Under `--strict` it is read as `@<quality-check-kind>`. |
| kind-of-quality-check tag | A tag naming a `kind of quality check`: `@unit`, `@integration`, `@e2e`, `@performance` or `@fitness`. Each one on an `executable claim` raises one `evidence obligation`. |

### Claim codes

| Term | Meaning |
|---|---|
| feature code | The `<FFF>` in `@CLM-<FFF>-<NNN>`: two to five uppercase letters or digits, declared on the line above a feature file's `Feature:`. |
| shared claim code | A code two scenarios have. Each scenario is a claim of its own, with its own Claim Reconciliation under the code. Each of its Quality Check Reconciliations for a quality check it asks for reads `duplicate-claim-code`. A scenario that asks for none reads `no-quality-check`. An evidence observation citing the code credits neither and posts to the unnamed claim. |
| known feature code, unknown feature code | A feature code is known when a feature file in `features/`, at the top of the repository, is headed with it. `allocate` refuses an unknown feature code unless `--new` is given. |

### The corpus, the report's views and term spelling

| Term | Meaning |
|---|---|
| corpus | The feature files under `--features`, whose scenarios one run reconciles. |
| Out of balance by feature | The Summary subsection `### Out of balance by feature` (`totals.outOfBalanceByFeature` in the JSON). It has one row per feature file, with how many of its claims are out of balance. A phantom claim and the unnamed claim are on no feature's row. The Markdown leaves the subsection out when no feature file has an out-of-balance claim. The JSON includes it, empty. |

### The report's and the command's words

These name what the tool shows a reader. They are not terms of the domain.

| Term | Meaning |
|---|---|
| report destination | Where a `--format` sends its report: standard output, or the file named after the colon. |
| source SHA | The target's commit, by default its resolved `HEAD`. |
| tool SHA | The commit of the tool's own checkout, when the tool runs from one, never the target's. A tool installed as a package has none. |
| run integrity | The report section `## Run integrity` (`runIntegrity` in the JSON). The Markdown prints it only when some evidence never ran. The JSON always includes it, with an empty list when none did. It lists each `never-ran` `evidence observation`, with its `kind of quality check` and where to look. Such a run is `unsound`. |
| highest seen | The highest code `allocate` found for a feature code, with where it was seen. |
| excluded claim code occurrence | A claim code written with its `@` anywhere in a feature file except on a scenario's tag line, such as in a title, a step, an Examples cell or a comment. No claim reads it. When there are any, the `Summary` counts them (`totals.excludedClaimCodeOccurrences` in the JSON). |

## Borrowed from 3F Consulting's delivery methodology

These terms are only named here. The methodology is not published: [`user-guide.md`](./user-guide.md) describes each term it uses, as spec-controller reads it.

- **Kinds of quality check**:
  - the kinds of quality check `@unit`, `@integration`, `@e2e`, `@performance` and `@fitness`, the first four the layers;
  - fitness function;
  - the adoption states `new-client`, `annotated` and `conformant`;
  - runner; the reconciler; `ci-run-time`, the CI pipeline timing its own suites, a fitness function; threshold.
- **Evidence codes and deferral scopes**: the `@CLM-<FFF>-<NNN>` claim code; feature code; the `@wip` and `@<quality-check-kind>pending` deferral scopes.
