# spec-controller's ubiquitous language

This glossary lists the words spec-controller's code, scenarios, report and help use, and what each means. It has two parts. The **domain terms** are spec-controller's own and are defined here. The terms **borrowed from 3F Consulting's delivery methodology** are named here: that methodology is not published, so they are described where [`user-guide.md`](./user-guide.md) uses them.

Each definition restates what spec-controller already says in [`user-guide.md`](./user-guide.md), its feature files or its report. The evidence model's definitions also state the reconciliation model those sources follow. If this file and the behaviour ever disagree, the behaviour wins and this file is corrected.

**One vocabulary across every surface**: code identifiers, JSON keys, Markdown headings, and a database schema if there ever is one. You read a machine key as much as you read prose, so it gets no private dialect.

**One term, three forms — the form follows the surface, the word never changes, and a term from this file is `backticked` wherever it appears.**

- Prose spells it out: `static check`, `phantom claim`.
- A handle hyphenates it: `static-check`, `phantom-claim`, `quality-check-kind`, `no-quality-check`.
- A code identifier camel-cases it: `staticCheck`.

A handle is not a licence to abbreviate. `check` is not a short form of `static-check`; it is a different word.

The **Double-check** entry of an evidence-model term names the words that have been seen standing in for it. Such a word means the term only where it is used in the term's sense.

## Domain terms

### The evidence model

Correctness is the agreement of two independent records. The debit side is the `Evidence Obligations` written in the test specifications. The credit side is the `Evidence Observations` seen when those tests run against the real code. Each term carries the bookkeeping term it borrows, which explains the analogy.

#### The subject

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Behaviour` | One thing the **`Application code`** should do, stated so it can be proved. A scenario describes a `behaviour`. The `Evidence Obligations` of a `behaviour` are the ones its scenario raises, one for each `kind of quality check` the scenario names. Its `Evidence Observations` exercise it against the real code. `Behaviour` is what the **`Test Specification`** exists to describe: it is the reason a scenario is written at all, and the thing `never-ran` says was never exercised. | Transaction — the real-world event an entry records | feature; functionality |
| `Application code` | The system under test: the reality that `evidence observations` are evidence of. It is on the credit side, but it is *not an entry itself*. | *(the subject the books describe)* — the real-world thing the accounts account for | |
| `Document specification` | Written intent: a document saying what the **`Application code`** should do, covering its behaviour and its fitness. A manifesto, a proposal and a technical design are examples. It is needed to make intent clear enough to build from, but it is never sufficient, because a document is not evidence. Its life is meant to be short: once **`executable specifications`** express it, they are the current truth. `balance` never reads one, so whether the checks say what the document says is judgement, not reconciliation. | Source documents — the contracts and invoices the entries are vouched against | spec, the spec (unqualified, where it could mean either kind) |
| `Executable specification` | A specification that states what the application must do and is run against it by a `quality check`: a scenario, a unit test or a fitness function. It is the preferred kind of specification, because running it is the evidence. The **`Test Specification`** is the collection of them. | *(the entries themselves)* — what the books record | living documentation (the field's other name, kept as a synonym); the Gherkin spec |

#### The `claims` — an executable claim, a phantom claim or an unnamed claim

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Claim` | What one `Claim Reconciliation` is about: a statement the evidence is weighed against. A claim is one input and one outcome. It is one of three kinds: an **`executable claim`**, a scenario or a row of an Outline with a `clm` column; a **`phantom claim`**, named by evidence and written nowhere; or the **`unnamed claim`**, for evidence that names no claim. Every `evidence observation` lands on exactly one claim, and each claim has one **`Claim Reconciliation`**. In the JSON report, each Claim Reconciliation's `claim` key holds its claim: an executable claim's `file`, `title`, `obligations` and, when it has one, `claimCode`; a phantom claim's `claimCode` alone; or nothing, for the unnamed claim. | *(the thing an account is opened for)* — the subject an account is kept about | real or invented scenario; invented scenario |
| `Executable claim` | A claim written to be executed: a scenario, or a row of a Scenario Outline with a `clm` column, on the surface of the `quality checks`. Its tags raise its `evidence obligations`, and its implementations (unit tests, step definitions, performance tests, CI steps) cite its claim code. `balance` shows whether both layers, the surface and its implementations, are there: a balanced executable claim is one whose implementations answer every check it asks for, and a *missing* one is an executable claim whose implementation layer has given no evidence. An `executable claim` is a post in the debit journal, and its claim code is what an **`evidence observation`** cites to post against it. A claim in a `document specification` is not one until it is written on the surface. | *(the thing an account is opened for)*: an account opened for a real subject | feature-file claim; written claim; specified claim; scenario (for the kind, since a row of an Outline with a `clm` column is one too) |
| `Phantom claim` | A claim the evidence names and nobody wrote: a cited claim code that no `executable claim` carries. A `Claim Reconciliation` is kept for it (`outcome` *cites-unknown-claim*). There is one per fabricated code, and it is always out-of-balance. Evidence citing the code of a deferred scenario lands on one too, since a deferred scenario is no `executable claim`. | Posting to a non-existent account — a posting naming an account that does not exist | ghost (as a top-level kind); undeclared (for a fabricated scenario); phantom scenario |
| `Unnamed claim` | The placeholder claim a `Claim Reconciliation` is kept for when no one `executable claim` can take its `evidence observations`. These are the observations that ran citing no claim code, several codes, or a code several `executable claims` share, and those posted as not recorded (`outcome` *cites-no-claim*), and those that never ran and name no claim or a code several `executable claims` share (`outcome` *never-ran*). It is one bucket, always out-of-balance. An `evidence observation` that never ran and names a claim posts to that claim's `Claim Reconciliation`. | Suspense account — an account holding postings that match no real account | unattributed (as a top-level kind); suspense scenario; observed claim |

#### The debit side

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Test Specification` | The **`executable specifications`** taken together: feature files (`@`-tags), step definitions and test code. It is the record of the **behaviours** to be proved and the `Evidence Obligations` for each. | Debit journal — the book of original entry for debits | |
| `Evidence Obligation` | An `executable claim` raises one for each `kind-of-quality-check tag` that applies to it, to be met by `Evidence Observations`. The `@`-tags on the scenario name those kinds: the `layers` `@unit`, `@integration`, `@e2e` and `@performance`, and `@fitness`. A row of an Outline takes its Outline's tags. A deferred scenario raises none. | Debit — the entry for what an account requires | demand, declare, require, insist, expect — every inflection (demanded, demander, declared, undeclared, required, requirement, …); obligation (bare); the `Declared` prefix |

#### The credit side

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| The run reports | Raw vitest / cucumber output: reality's record. | Credit journal — the book of original entry for credits | |
| `Static Check` | A source code check run over the actual code, such as an ESLint rule, a type check or a custom script. It is a fitness function assessed *statically*, as opposed to one assessed by running the suite (`coverage`, `mutation`, `ci-run-time`). Its run produces one **`evidence observation`** of the `fitness` `kind of quality check`. `Static check` names only this source-reading subset, never fitness functions in general. **How its evidence posts:** a fitness function's evidence observation, static or run, **cites its claim code** only when the step record names its step. A step the step record does not name is posted as not recorded, citing no code. Where it lands is the ordinary three-way answer, not a special case. If it cites the claim code of a **real `executable claim`** that raises the evidence obligation, it posts there. If it cites a claim code **no `executable claim` carries**, it posts to a **`phantom claim`** (`outcome` *cites-unknown-claim*). If it cites **nothing**, several codes, or a code two scenarios share, it posts to the **`unnamed claim`** (`outcome` *cites-no-claim*). It is surfaced either way, never omitted. | *(the instrument that produces a credit)* — what the credit journal records the running of | static guard, `staticGuard`, `<static-guard>`; guard (bare noun, for a fitness function); check (bare) |
| `Dynamic Check` | A fitness function assessed by **running** the code, or by measuring a run: `ci-run-time`, `coverage`, `mutation`, `crap`, `reconciliation`. It is the other kind of fitness function besides a `static check`; neither names the class as a whole. Its evidence posts exactly as a `static check`'s does. It is not Ford, Parsons and Kua's *dynamic* fitness function, which names a shifting threshold (*Building Evolutionary Architectures*, ch. 2, *Result: Static Versus Dynamic*). Here *static* and *dynamic* say how the evidence is obtained, as in static and dynamic analysis. | | static check (for a fitness function assessed by running) |
| `Evidence Observation` | One reported result of a test or a fitness function, of one shape whatever its source: the codes it cites, its result (passed, failed, passed-on-error, never-ran or not recorded), its `kind of quality check`, where to look, and what it said. It is `attributed` by the code it cites: to the one `executable claim` that carries the code, to a `phantom claim` when no `executable claim` carries it, and otherwise to the `unnamed claim`. One that never reached its assertions is `never-ran`: it was reported, but did not run to a result. One whose CI step the step record does not name is not recorded: `balance` has no word on how it went, so it is never passed and never credits a claim. | Credit — the entry for what an account is provided | observation (bare); credit, credit side (in a sentence that names no debit); supply; execution; declared (for evidence) |
| `Freshness` | An `Evidence Observation`'s validity window. Evidence proves the code *as it is now*, so an evidence observation from an earlier state is not evidence for this one. Every evidence observation `balance` reconciles comes from the build being reconciled, which regenerates its reports in the same run. The window is therefore **this build**, and it never surfaces. A check too slow for every push, such as a nightly `mutation` sweep, runs on its own schedule and posts nothing to a push's `Claim Reconciliations`. A sweep that stops running is a lapse, stopped where work starts, and never a `missing` row. `Freshness` adds no `Outcome` and puts no clock inside the reconciliation. | Cut-off — a transaction counts only in the period it belongs to | |

#### Posting

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Attribution` / `attributed` (by claim code) | Tying an `evidence observation` to its `executable claim`. A debit self-posts by living in the scenario. **One rule: the evidence observation cites.** An `evidence observation` cites the claim code of its `executable claim`: a behavioural test cites its stepped scenario, and a fitness function's run cites its own. One evidence observation names one `executable claim` and posts to exactly one `Claim Reconciliation`, where it is one `Quality Check Reconciliation`. **One that cites more than one `executable claim` credits none of them** and posts to the unnamed claim, keeping each code it cites, whatever the runner: no reader picks one. One that posts to no real `executable claim` is **phantom** (its claim code names no real `executable claim`) or **unnamed** (it cites nothing). How it cites is set out under *How an evidence observation cites*, below. | Posting — recording a journal entry into its account | name-match, name-matched (posting) |
| `Quality Check` | One check: one tool's run, such as ESLint's, that assesses the product against a quality characteristic. Each `evidence observation` a quality check produces carries one **`kind of quality check`** and is matched on that kind. One run can produce evidence of more than one kind, as one `cucumber-js` run serving two `layers` does. A **`Quality Check Reconciliation`** matches an `evidence obligation` and an `evidence observation` within a `claim` on their `kind of quality check`. | *(the instrument a credit is booked from)* — one source of entries | check (bare) |
| `Kind of quality check` | A **`kind of quality check`** (`qualityCheckKind`) is the key an evidence obligation is raised by and its evidence matched on. There are five, flat peers: the four **`layers`** `unit`, `integration`, `e2e` and `performance`, and `fitness`. A scenario names its kinds of quality check by its tags and raises one `Evidence Obligation` per tag. A check of a **`layer`** is an example of a `behaviour` on a stepped scenario. A **fitness** check is a whole-system property against a `threshold`, and **one `@fitness` scenario is one check**: it is identified by its claim code and described by its title. Several fitness functions are several scenarios, as the CI pipeline's two timed suites are two. Nothing classifies a fitness function further: no characteristic word, no roster, no roll-up. The behavioural/fitness grouping lives in the model and the docs, **never in the tag**: no `@behavioural=unit`, no `@fitness=complexity`. A fitness function may be assessed by **reading** the source (a **`Static Check`**: ESLint, `tsc`) or by **running** the suite (coverage, mutation, CI run time). That is a property of the check, not a difference in how its evidence posts: every evidence observation cites its claim code (see `Attribution`). The CI pipeline timing its own suites is the prototype of the fitness shape: an `@fitness` scenario, with the measured time citing its claim code. It is never carved out as harness, and never named so as to dodge reconciliation. | *(the sub-account coordinate)* — the key an entry is classified and matched by | quality check (for one of the five); tier (for a layer); runtime (for the layers `@unit`, `@integration`, `@e2e`, `@performance`); level, (kind, level) — the two-axis grid; `lint` (as a catch-all for fitness functions); characteristic (a word classifying a fitness function); `@fitness=<check>` or any group-prefixed check tag |
| `Layer` | One of the four behavioural kinds of quality check, `unit`, `integration`, `e2e` and `performance` (`Layer` in the code). The runner the target declares for a layer, when it declares one, runs that layer's tests or scenarios. `fitness` is the one kind of quality check that is not a layer. | | tier; behavioural check (for a layer) |
| `Claim Reconciliations` | The `evidence obligations` (debits) and `evidence observations` (credits) organised by **`claim`**, one `Claim Reconciliation` for each, and keyed by `kind of quality check`. This is where reconciliation happens. The **`Evidence Reconciliation`** is the whole: the `Claim Reconciliations` and the `Summary` over them. **Every `evidence observation` posts to exactly one `Claim Reconciliation`, never to none.** An evidence observation that posts nowhere has vanished from the books, which is the fault the `Claim Reconciliations` exist to make impossible. An evidence observation that cites the claim code of one `executable claim` posts there, whatever its `kind of quality check`. One citing no real `executable claim` still posts, to a **`phantom claim`** or the **`unnamed claim`**. Posting is not classifying: an entry posts here whatever it later reconciles to, including nothing. | Ledger — the accounts with their posted debit and credit entries, by account | ledger (for the collection) |

#### How an evidence observation cites

There is one form per runner, and nothing else. The scenario's tag line (`@CLM-<FFF>-<NNN> @unit @e2e`) raises the `evidence obligations`. Each `evidence observation` then reaches that scenario by the one form its runner's report can carry:

| `kind of quality check` | the evidence observation | the form that cites | example |
|---|---|---|---|
| `unit` | a Vitest assertion | a bracketed `[CLM-…]` in its `it` title, else in an enclosing `describe` title; the most specific wins | `describe("[CLM-<FFF>-<NNN>] a feature code whose highest live claim code …", …)` |
| `integration`, `e2e`, `performance` | the Cucumber report's run of the scenario | the scenario's own claim code, which the report carries | the same `@CLM-<FFF>-<NNN>` tag line, as Cucumber reports it |
| `unit` | a pytest test, in its JUnit XML report | `clm` properties on its `<testcase>` naming exactly one claim code, a code written twice counting once, which a `@pytest.mark.clm` marker and a `conftest.py` hook write | `@pytest.mark.clm("CLM-<FFF>-<NNN>")` on the test |
| `fitness` | the CI step that runs the check, read on its `outcome` | the step's `id:` | `id: CLM-FIT-<NNN>` on the step, against `@fitness @CLM-FIT-<NNN>` |

**A citation form counts only when a reader is built for it.** Nothing reads a bare or `@`-prefixed code in a test title, a marker comment in a step-definition file, a code in any other comment, a Playwright spec or a k6 script. Such a form cites nothing, so the evidence observation it was meant for posts to the **unnamed claim**. The four forms are the whole mechanism. The readers in [`packages/core/src/inputs/`](../packages/core/src/inputs/) hand over each title, `clm` property, tag and step `id:` as written, and [`packages/core/src/domain/postEvidenceObservation.ts`](../packages/core/src/domain/postEvidenceObservation.ts) reads the code each cites, by the one form in [`packages/core/src/domain/claimCodes.ts`](../packages/core/src/domain/claimCodes.ts).

#### Two links, one shape

Reconciliation has two links. The first judges a `document specification` against the `quality checks`, and spec-controller has no command for it; `balance` judges the `quality checks` against the `Application code`. A claim can appear in three places: in prose, in the document specification; in the quality checks, in two layers, the surface (a feature file, whose `executable claims` raise `evidence obligations`) and its implementations (unit tests, step definitions, performance tests and CI steps); and in the check results, as `evidence observations`. A codebase may have any of these, or none.

Each link has two sides, and the table below gives both links the same cells. Each keeps its own words for them, so a reader can see they are parallel without their being merged:

| | spec ↔ checks | checks ↔ application (`balance`) |
|---|---|---|
| **The two sides** | the document specification / the quality checks | `evidence obligations`, raised by the surface / `evidence observations`, from the implementations running against the application |
| **On both sides, agreeing** | met | `satisfied` |
| **On the first side only** | unmet: a claim in the document specification with no quality check | `missing`: an obligation with no observation |
| **On the second side only** | unstated: a quality check of behaviour the document specification does not state | `not-asked-for`; `cites-unknown-claim`, a `phantom claim`; `cites-no-claim`, the `unnamed claim` |
| **On both sides, disagreeing** | conflict: the document specification and a quality check assert different outcomes | `failing`: the check ran, and the application did not do what it checks |
| **On both sides, but the evidence cannot be trusted** | | `never-ran`: the check never reached its assertions; `cannot-fail`: the check passed, but its step or its job sets `continue-on-error`, or `balance` cannot read whether it does, so its red might not fail the build |
| **The claim is written so it cannot be reconciled** | | `no-claim-code`: the claim carries no code; `duplicate-claim-code`: two claims share one code; `no-quality-check`: the claim asks for no quality check, carrying a claim code and no kind-of-quality-check tag, and nothing cites it |

A structural contract, on the spec ↔ checks link, is not a claim at all: a test asserting an invariant rather than one input and one outcome.

#### Reconciling

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Balancing off` | Reconciling one `claim`, its `evidence obligations` against its `evidence observations`, matched on their `kind of quality check`, into its `Claim Reconciliation`. | Balancing off — computing one account's balance | |
| `Quality Check Reconciliation` | One entry of a `Claim Reconciliation`, with its own **`outcome`**: an `evidence obligation` and the `evidence observation` of its `kind of quality check` that answers it, an `evidence observation` with no `evidence obligation` to answer, an `evidence obligation` no `evidence observation` that ran answers, or neither, for a claim with a claim code that asks for nothing and has no evidence. A claim with no claim code that asks for nothing has one entry, `no-claim-code`, with neither side. No entry stands in for another `evidence observation`: two passing tests are two *satisfied* entries, and a passing and a failing test are a *satisfied* and a *failing* one. They are sorted by `kind of quality check` (unit, integration, e2e, performance, fitness), then by where their tests are, then by the codes they cite and the rest each records, so two runs over the same evidence list them in the same order. The Markdown lists those not *satisfied* as the claim's `reconciling items`. | Line item — one entry in an account | sub-account; reconciled evidence obligation; line; item; picked outcome |
| `Outcome` | The eleven-valued result of a `Quality Check Reconciliation`: `satisfied`, `failing`, `cannot-fail`, `missing`, `no-claim-code`, `duplicate-claim-code`, `not-asked-for`, `cites-unknown-claim`, `cites-no-claim`, `never-ran` and `no-quality-check`. It is one thing in two representations: the **`outcome` handle**, the short machine name the code and both reports carry (`missing`, `not-asked-for`), and the `outcome` itself, the sentence the reconciliation asserts. The sentence is the valuable half, because it is checkably true or false of a case, where the handle is only a label. Settle a dispute by asking whether the sentence is true of the case, never by arguing what the handle connotes. | *(whether a sub-account balances, and how)* — the balance-status of one sub-account | state; outcome tag (a `tag` is authored in a feature file; a handle is computed); the flat triad attributed / ghost / unattributed; `undemanded` (for `not-asked-for`); uncoded (for `no-claim-code`) |
| `Claim Reconciliation` | The evidence reconciled for one **`claim`**: its `Quality Check Reconciliations`. It carries a **`verdict`** and its **`reconciling items`**. Its claim is one of three kinds: an **`executable claim`** (written in a feature file), a **`phantom claim`** (cited, but no feature defines it), or the **`unnamed claim`** (evidence citing no code, several codes, or a code two scenarios share). The collection is the **`Claim Reconciliations`**, and *never* scenarios or `claims`, since each is the reconciliation of a claim, not the claim. | Account — the record for one thing that carries a balance | account; scenario balance; scenarios (for the collection); Scenario Reconciliation |
| `Verdict` | The **two-valued** roll-up of a `Claim Reconciliation`, and never a third value. It is *balanced* when every `Quality Check Reconciliation` on it is *satisfied*, and *out-of-balance* when there is any `reconciling item`. A `phantom claim`'s or the `unnamed claim`'s reconciliation is always out-of-balance. An `executable claim` with neither `evidence obligation` nor `evidence observation` is out-of-balance via `no-quality-check`, or `no-claim-code` when it has no claim code (one whose tests run untagged is out-of-balance via `not-asked-for`, and one that asks for a quality check under a claim code another shares via `duplicate-claim-code`), never a separate "empty" `verdict`. | Balanced / out of balance — an account whose two sides agree / don't | |
| `Reconciling item` | A `Quality Check Reconciliation` whose `outcome` is not *satisfied*. A `Claim Reconciliation` out of balance lists every one, each typed and none ranked. It has three shapes: a debit-side exception (missing / failing / `cannot-fail` / no-claim-code / duplicate-claim-code), a credit-side exception (cites-unknown-claim / cites-no-claim / not-asked-for / never-ran), or **neither**, which is a real `executable claim` with a claim code, no `evidence obligation` and no `evidence observation` (no-quality-check). no-claim-code is always debit-side, because the claim code is missing from the scenario, whether or not the claim asks for a quality check. | Reconciling item — a line explaining a difference between two records | |
| `Cannot-fail` | A passing `evidence observation` whose check's CI step or job sets `continue-on-error` to anything but `false` (`true`, or an expression such as `${{ matrix.experimental }}`), so its red might not fail the CI run; the *`cannot-fail`* `outcome`. It is green on the outside, and nothing behind it need hold the build. It is read from the step record: such a step's recorded success is *cannot-fail*, and the step's own `outcome` answers a swallowed red, so it reads *failing*. A step the step record does not name is not recorded, never *cannot-fail*. A recorded success whose step no workflow `balance` read has is *cannot-fail*, since `balance` cannot read whether it allows failure. The step record does not say what the check examined, so a check over zero files that exits 0 is *satisfied*, not a pass that cannot fail. | | fabricated; green-but-fake |

#### The whole run

| Term | Meaning | Bookkeeping term | Double-check |
|---|---|---|---|
| `Evidence Reconciliation` | The whole reconciliation: the `Claim Reconciliations`, the `Summary` over them with the `run verdict`, the step account, the provenance, and the errors in the inputs and the run integrity, each empty when the run had none. It is the key concept the domain models, and the report renders it. | Trial balance — the statement of all account balances | trial balance (kept as the bookkeeping root of the metaphor); self-reconciliation, `self-balance` (names for the reconciliation check) |
| `Summary` | The report's `## Summary` section: the *Run verdict*, then the totals. They count the `Claim Reconciliations`, total, balanced and out of balance, and the claim codes written where no claim reads them; the `Quality Check Reconciliations` by `kind of quality check`, each kind with its `Evidence Obligations`, its `Evidence Observations` and a count for each `outcome`, a row for what names no kind, and an *All* row over them; the `Evidence Observations` by the kind of claim they were filed on; and *Out of balance by feature* when any claim is. Its JSON key is `totals`. | *(the totals — no distinct classic term)* — the aggregate of the trial balance | headline tallies |
| `Claim code errors` | A whole-run section of the report listing faults in the claim **codes** themselves, inside `## Errors in the inputs` (`errorsInTheInputs` in the JSON); its JSON key is `errorsInTheInputs.claimCodeErrors`. **`foreign-claim-code`**: a scenario's code names a feature other than the one it sits in. **`no-feature-code`**: a feature file carries no header code while its scenarios carry ids. **`duplicate-feature-code`**: two feature files claim one feature code. **`several-claim-codes`**: one scenario carries more than one claim code, so, as on the credit side under `Attribution`, no reader picks one, and it raises its evidence obligations under none of them. **`claim-code-beside-clm-column`**: an Outline carries a claim code of its own or on an Examples block, and has a `clm` column, so it raises its evidence obligations under neither its code nor any row's. The section is **neither a `reconciling item` nor a roll-up of `verdicts`, and it leaves the run not reconciled on its own** (`claim-code-errors`): a run can fail for a reason that is not any `executable claim`'s `verdict`. The first three leave every posting unambiguous: what is wrong is the codes, not a `Claim Reconciliation`'s balance. A duplicated claim code is deliberately **not** here. Each `executable claim` carrying it is its own `Claim Reconciliation`, which cannot reconcile, so it sits on the rows as `duplicate-claim-code`, and evidence citing the code credits none of them and posts to the unnamed claim. | *(a fault in the chart of accounts, not in any account)* — the books cannot be read until the coding is fixed | chart of accounts; coding errors; uncoded (for `foreign-claim-code` or `no-feature-code`) |
| `Unsound` | A run carrying any `never-ran` `Quality Check Reconciliation` is **`unsound`**. This is a derived whole-run reason, not an `outcome`: the run is `not reconciled`, exit 3, because the evidence could not be trusted to reconcile. It comes before every other reason. | | |
| `--strict` | The run mode that reads every claim as if nothing were put off: a `deferral tag` is ignored, so its scenario is an `executable claim`, and `@<quality-check-kind>pending` is read as `@<quality-check-kind>`, raising that `evidence obligation`. It changes no exit code. | | |

### The commands and the run

| Term | Meaning |
|---|---|
| `balance` | The command that reconciles the Gherkin scenarios against the test and CI evidence and writes the Evidence Reconciliation. It is a gate: an out-of-balance run exits `1`. |
| `allocate` | The command that prints the next claim code for a feature code: one past the highest code the repository has ever carried, whether written under `CLM` or under the retired `SCN`. |
| evidence report | A report a test runner writes, which `balance` reads as runtime test evidence: the Vitest, Cucumber, pytest, Jest, JUnit or RSpec report, each named by its own flag. |
| report of test results | An evidence report of tests that are not scenarios run step by step: the Vitest, Jest, pytest, JUnit or RSpec report. Its fallback is `unit`. |
| report of scenario runs | An evidence report of Gherkin scenarios run step by step: the Cucumber report. Its fallback is `integration`. |
| fallback | The `kind of quality check` an evidence report posts an evidence observation at. A report of test results posts every observation there. A report of scenario runs posts an observation at each `layer` its scenario is tagged with (`@integration`, `@e2e` or `@performance`), and at its fallback only when the scenario carries none. |
| report destination | Where a `--format` sends its report: standard output, or the file named after the colon. |
| `--exit-zero` | Writes the same report as without the flag, but exits `0` on an out-of-balance run verdict. It never changes the exit code of a run that is not reconciled (`3`), a usage error (`2`) or an unexpected error (`4`). It is the on-ramp before gating. |
| run verdict | What the whole run comes to, and its exit code: `balanced` (`0`), `out-of-balance` (`1`), or `not-reconciled` (`3`) with why. When several reasons apply, `unsound` comes first, then `claim-code-errors`, then `nothing-to-reconcile`, all before out of balance. A run that cannot reach a verdict gives none. A run that reaches its verdict keeps its exit code. |
| not reconciled | The run verdict of a run `balance` cannot rely on, naming why: `unsound`, when some evidence never ran; `claim-code-errors`, when a claim code is misfiled; or `nothing-to-reconcile`, when there are no Claim Reconciliations. It exits `3`, even under `--exit-zero`. In the JSON it is `runVerdict.verdict` `not-reconciled`, with `runVerdict.why`. |
| nothing to reconcile | There is no Claim Reconciliation at all, so the run has no basis for a verdict: it is `not reconciled` (exit `3`). |
| unexpected error | An error nothing else handles. Before the run verdict it stops the run with no verdict, at exit `4`; after it, the run keeps its verdict's exit code. |
| usage error | A malformed invocation, refused before anything runs (exit `2`). |
| error code | The stable code a refusal shows its reader in square brackets at the start of its line, such as `[unknown-flag]`, so the refusal can be quoted and looked up in the user guide whatever its words. An error in the inputs gives its code in the report. An unexpected error's line carries `unexpected-error`, and nothing that is not an error carries one. |
| target | The repository being reconciled. `--target` names it in the report's provenance; without it, the provenance names the git checkout's `origin`, or `unknown-target`. |
| provenance | The report's record of what was reconciled: the target, its source SHA, the tool SHA when there is one, the tool version, the time the run started, and the inputs the run read with their paths. So a reconciliation is reproducible and attributable. Its JSON key is `provenance`. |
| source SHA | The target's commit, by default its resolved `HEAD`. |
| tool SHA | The commit of the tool's own checkout, when the tool runs from one, never the target's. A tool installed as a package has none. |
| run integrity | The report section `## Run integrity` (`runIntegrity` in the JSON). The Markdown prints it only when evidence never ran; the JSON always has it, its list empty when none did. It lists each `never-ran` `evidence observation`: its `kind of quality check` and where to look. Such a run is `unsound`. |
| proof never ran | An `evidence observation` that never ran to a result, so the behaviour it proves was never exercised: a `never-ran` one. |
| Evidence Observations (the total) | The `Summary`'s count of evidence observations over every `kind of quality check`, fitness included, and its balancing identity: every evidence observation lands on an `executable claim`, a phantom claim or the unnamed claim, and the three counts sum to the total. |
| errors in the inputs | The report section `## Errors in the inputs` (`errorsInTheInputs` in the JSON). The Markdown prints it only when the run found any; the JSON always has it, its lists empty when there are none. It holds the `Claim code errors` and the `configuration errors`, each a line giving its code, then what it is about. |

### Fitness functions in CI

| Term | Meaning |
|---|---|
| pipeline step | A step of a CI job, as the pipeline declares it: it runs a command or uses an action. |
| discovery scope | The CI workflows `--ci` names. Every step of every job in them is read. |
| non-check | A step the target names under `specController.notChecks`, unless it is a reconciler step. The `step account` counts it under *Non-checks* (`nonChecks` in the JSON). Double-check: *Excluded*, a word seen standing in for it, means a non-check only where it is used in this sense. |
| plumbing step | A step that only sets up the job: it checks out the source, caches, sets up a toolchain, or moves artefacts between jobs. It is neither a check nor a runner. The CI workflow's reader says which steps are plumbing. The `step account` counts them under *Plumbing* (`plumbing` in the JSON). A plumbing step the manifest also names a non-check is a non-check: it is counted with the non-checks. |
| variant | One of the ways of writing an input that `balance` treats as the same, such as a launcher (`npx`, `uv run`) before a runner, or a package manager's way of running a script. One claim stands for each kind of input, and its variants are listed in a `*.variants.json` data file beside the code that reads them, keyed by that claim's code. There is one for the shell reader, the workflow reader, the manifest reader, the Markdown report's quoting of names, and the counting of claim codes in comments. [`shell.variants.json`](../packages/core/src/inputs/shell.variants.json) holds the ways a step's command reaches a runner: the launchers, the wrappers and `xvfb-run`'s options, the package managers' ways of running a script, the runners named in several words, the command lists a runner may stand in, and the pipes onward that leave it a check. The places a step can write the step record from (`run:` and `env:`) and the plumbing actions are in [`workflows.variants.json`](../packages/core/src/inputs/workflows.variants.json). A way of writing one not listed is not read as that kind. Double-check: *form*, *spelling*. |
| fitness function | A step in the discovery scope that is not a declared runner, the reconciler, a non-check or a plumbing step, and a runner step whose `id:` is a claim code the step record has. The `step account` counts it under *Fitness functions* (`fitnessFunctions` in the JSON). |
| uncited fitness function | A fitness function whose step cites no claim. Its `evidence observation` lands on the unnamed claim. |
| step account | The report's account of the CI steps the run read, `## Step account` (`stepAccount` in the JSON). The Markdown prints it when the run read a CI workflow step, so every step read is accounted for; the JSON always has it, with no rows when none was read. It has a row per workflow and job counting the steps read, then the steps by disposition (runners, reconciler steps, non-checks, plumbing, fitness functions), and a total over the rows, which the Markdown prints when there is more than one job. |
| check step | The CI step that already runs a check, carrying the check's claim code as its `id:`. |
| citation | The claim code on a check step's `id:`: a citation of the scenario, never a definition of the check. |
| converted fitness function | A fitness function whose CI step carries its `@fitness` scenario's claim code as its `id:`, so `balance` credits its result, read from the step record, to that scenario. |
| unconverted fitness function | A fitness function that runs in CI with no claim code as its step's `id:`. `balance` finds it running through the step record when its step has an `id:`, as an uncited fitness function; a step with no `id:` is never in the step record, and is posted as not recorded. |
| step record | The CI run's own record of what each of its steps did: the `toJSON(steps)` dump `--ci-steps` reads. |

### Configuration

| Term | Meaning |
|---|---|
| `specController` block | The block in a target's `package.json` holding `runners`, `notChecks` and `deferralTags`. |
| `runners` | The declared behavioural runners, keyed by the four `layers` and nothing else. A value is a runner's name, or `null` to say the layer has none. |
| `notChecks` | The target's list of steps that are neither runners nor checks, each written `<workflow file>:<job id>:<step name>` and matched exactly. Such a step is reported as a non-check, unless it is a reconciler step. An entry that matches no step of a workflow the run read, or does not name a step in that form, makes no step a non-check and is named among the configuration errors. An entry naming a workflow the run did not read is not judged. |
| configuration errors | The `specController` entries the run could not use, in `## Errors in the inputs` (`errorsInTheInputs.configurationErrors` in the JSON): one of the wrong kind, read as absent (`configuration-wrong-kind`); a key the block does not read (`configuration-unknown-key`); a `runners` key that is not a layer (`runner-key-not-a-layer`); or a `notChecks` entry that matches no step (`not-checks-entry-matches-no-step`) or names none (`not-checks-entry-not-a-step-name`). Each is named on the report, and none refuses the run. |
| deferral tag | A tag that puts a scenario off, on the scenario itself, on the Rule it sits under or on its Feature: it is not an `executable claim`, raises no evidence obligation, and posts nothing. Evidence still citing its code lands on a `phantom claim`. The built-in set is `@wip`, `@ignore`, `@skip`, `@todo` and `@pending`, and `deferralTags` extends it. Under `--strict` it is ignored. |
| `@<quality-check-kind>pending` | A tag that raises nothing: the scenario asks for no evidence of that one `kind of quality check`. Under `--strict` it is read as `@<quality-check-kind>`. |
| kind-of-quality-check tag | A tag naming a `kind of quality check`: `@unit`, `@integration`, `@e2e`, `@performance` or `@fitness`. Each one on an `executable claim` raises one `evidence obligation`. |

### Claim codes

| Term | Meaning |
|---|---|
| feature code | The `<FFF>` in `@CLM-<FFF>-<NNN>`: two to five uppercase letters or digits. |
| header code | A feature file's own code tag, the feature code its scenarios' codes are filed under. |
| account class | A feature file, as the class its scenarios' codes are filed under. |
| shared claim code | A code two scenarios carry. Each scenario is a claim of its own: it has its own Claim Reconciliation under the code. Each Quality Check Reconciliation for a quality check it asks for reads `duplicate-claim-code`; a scenario that asks for none reads `no-quality-check`. An evidence observation citing the code credits neither and posts to the unnamed claim. |
| known feature code, unknown feature code | A feature code is known when a feature file in `features/`, at the top of the repository, is headed with it. `allocate` refuses an unknown feature code unless `--new` is given. |
| highest seen | The highest code `allocate` found for a feature code, with where it was seen. |
| excluded claim code occurrence | A claim code written with its `@` in a feature file anywhere but on a scenario's tag line, such as in a title, a step, an Examples cell or a comment. No claim reads it. The `Summary` counts them, when there are any (`totals.excludedClaimCodeOccurrences` in the JSON). |

### The corpus, the report's views and term spelling

| Term | Meaning |
|---|---|
| corpus | The feature files under `--features`, whose scenarios one run reconciles. |
| Out of balance by feature | The Summary subsection, `### Out of balance by feature` (`totals.outOfBalanceByFeature` in the JSON), with a row for each feature file and how many of its claims are out of balance. A phantom claim and the unnamed claim are on no feature's row. The Markdown leaves it out when no feature file has one; the JSON has it, empty. |

## Borrowed from 3F Consulting's delivery methodology

These terms are named here. The methodology is not published: [`user-guide.md`](./user-guide.md) describes each term it uses as spec-controller reads it, and `ci-run-time` is described under `Dynamic Check`, above.

- **Kinds of quality check**:
  - the kinds of quality check `@unit`, `@integration`, `@e2e`, `@performance` and `@fitness`, the first four the layers;
  - fitness function;
  - the adoption states `new-client`, `annotated` and `conformant`;
  - runner; the reconciler; `ci-run-time`; threshold.
- **Evidence codes and deferral scopes**: the `@CLM-<FFF>-<NNN>` claim code; feature code; the `@wip` and `@<quality-check-kind>pending` deferral scopes.
